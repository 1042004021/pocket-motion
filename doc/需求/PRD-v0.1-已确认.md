## 2. 需求概述

### 2.1 背景

现有手机端 SD1.5 项目已经能在目标手机上通过 QNN/NPU 运行 SD1.5 图片生成，速度可接受。用户希望进一步验证能否在手机端生成短视频，并明确不接受 CPU/GPU 作为主要推理路径。

### 2.2 目标

验证以下组合能否完整运行在高通 NPU 上：

```text
SD1.5 + AnimateDiff-Lightning
256×256
8 帧
4～6 步
固定 shape
QNN HTP
```

先回答“能不能”，再决定是否做 Android UI 和产品化。

### 2.3 范围

**包含：**

- 目标设备能力探测：SoC、ABI、RAM、Android 版本
- QNN SDK 与模型转换环境检查
- AnimateDiff motion module 的 QNN 算子覆盖验证
- 固定 shape 的 8 帧最小推理链
- 真机延迟、峰值内存、温度、失败点记录
- 阻塞点与替代模型建议

**不包含：**

- 长视频、720p/1080p、实时生成
- SVD、Wan、CogVideoX 等大模型
- CPU/GPU 推理兜底
- 现有 Android App 正式 UI 接入
- 云端视频生成服务
- 模型分发和商业发行

## 3. 功能需求

### 3.1 设备与环境探测

#### 功能描述

通过 adb 和本机脚本确认目标设备、Python 环境、QNN SDK 路径和模型工具状态，输出可复核的 JSON 报告。

#### 验收标准

- [ ] 能读取设备型号、SoC、ABI、Android 版本、内存
- [ ] 能检测 Python、torch、ONNX、ONNX Runtime、QNN SDK 环境
- [ ] 缺失项明确列出，不把缺失环境当成通过

### 3.2 AnimateDiff QNN 算子覆盖

#### 功能描述

把 AnimateDiff-Lightning 的 motion module 及相关时序计算转换为 QNN 可分析图，检查关键算子是否支持，并记录必须回退的算子。

#### 验收标准

- [ ] 输出算子覆盖报告
- [ ] 明确是否存在只能回退 CPU/GPU 的算子
- [ ] 若无法全 NPU，给出阻塞点、可行性结论和替代方案

### 3.3 8 帧最小推理链

#### 功能描述

在固定 shape 下跑通 8 帧、256×256、4～6 步的最小视频推理，输出可视化帧序列。

#### 验收标准

- [ ] 不依赖 CPU/GPU 完成核心 UNet/motion module 推理
- [ ] 输出连续 8 帧图像
- [ ] 记录每段耗时、峰值内存和温度变化
- [ ] 如失败，保留失败日志和具体算子/模型层位置

### 3.4 可行性结论

#### 功能描述

基于实测给出是否继续做 Android 宿主、是否换模型、是否放弃 NPU 视频路线的结论。

#### 验收标准

- [ ] 文档记录推荐路线和不推荐路线
- [ ] 明确是否满足“NPU 全链路”要求
- [ ] 不以单次偶然成功作为结论

## 4. 非功能需求

- 所有推理验证必须可复现，记录设备、模型版本、QNN SDK 版本和命令
- 模型权重和二进制不入 Git
- 不在未确认许可证前分发任何模型权重
- 不以 CPU/GPU 结果冒充 NPU 结果

## 5. 风险

| 风险 | 影响 | 应对 |
|------|------|------|
| temporal attention 算子不支持 | NPU 全链路失败 | 记录阻塞，评估自定义 op 或换模型 |
| 固定 8 帧内存超限 | 无法在 12GB 设备运行 | 降分辨率/帧数/量化 |
| 量化后画质不可用 | 结果无产品价值 | 调整量化策略或换模型 |
| 持续推理热降频 | 生成时间不可接受 | 限制连续生成、记录温控曲线 |
| 模型许可证不清晰 | 不能分发 | 先核对权重和代码许可证 |
